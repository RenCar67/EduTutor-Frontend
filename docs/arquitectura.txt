Introducción y Alcance El presente documento describe la arquitectura de software de EduTutor, una plataforma distribuida de gestión de tutorías académicas. El sistema conecta estudiantes, tutores, coordinadores y administradores a través de un ecosistema de microservicios desacoplados, comunicación asíncrona (RabbitMQ y Apache Kafka), identidad federada corporativa (Azure AD) y un frontend Angular con control de acceso basado en roles. Los requerimientos del caso se organizan en cuatro macro-tareas que corresponden a capas arquitectónicas completas y sus dependencias directas: Macro-Tarea 1 — Infraestructura base, middleware y plataforma de mensajería (DevOps &amp; Event Brokers). Macro-Tarea 2 — Seguridad centralizada, identidad y capa de borde (IAM, API Gateway &amp; BFF). Macro-Tarea 3 — Ecosistema backend de dominio, persistencia y procesamiento asíncrono (Core &amp; CQRS). Macro-Tarea 4 — Frontend web, integración end-to-end y puesta en marcha (UI &amp; E2E). Cada sección detalla el diseño, los contratos técnicos, las decisiones de configuración y los criterios de resiliencia y observabilidad que gobiernan esa capa. 1.1 Vista General de la Topología [Angular SPA + MSAL] | HTTPS + Bearer JWT v [AWS API Gateway - JWT Authorizer] | (Azure AD issuer/audience) v [ms-edututor-bff] (Spring Security Resource Server) / \ v v [ms-edututor- [ms-edututor- catalog] sessions] | Oracle | Oracle |-- commands --&gt; [RabbitMQ] | q.cmd.email | q.cmd.session | q.cmd.certificate | | | v | [ms-edututor-notify] | (sin DB) | |-- domain events --&gt; [Kafka] sessions.events audit.timeline / \ v v [ms-edututor-audit] [ms-edututor-report] | Oracle | Oracle v v /api/audit/* /api/report/kpis, /top-services Infraestructura de ejecución: tres instancias EC2 dedicadas (ec2-apps, ec2-mq, ec2-kafka), cada una orquestada mediante Docker Compose modular, con Security Groups que exponen únicamente los puertos estrictamente necesarios (HTTP/HTTPS, AMQP 5672, Kafka 9092, y los puertos de administración internos restringidos por IP de operación). 2. Macro-Tarea 1 — Infraestructura Base, Middleware y Plataforma de Mensajería Esta capa cubre el aprovisionamiento de los tres entornos EC2, la orquestación de contenedores y las dos topologías de mensajería que sostienen el desacoplamiento asíncrono de la plataforma: RabbitMQ para comandos de trabajo puntuales y Kafka para streaming de eventos de dominio y auditoría. 2.1 Despliegue de Entornos (AWS EC2 &amp; Docker Compose) Instancia Rol Servicios en Docker Compose Puertos expuestos ec2-apps Cómputo de aplicación ms-edututor-bff, catalog, sessions, notify, audit, report 80/443 (ALB), internos 8080-8085 ec2-mq Broker de mensajería RabbitMQ 3 (con plugin management) 5672 (AMQP), 15672 (UI, restringido) ec2-kafka Streaming distribuido Zookeeper x3, Kafka broker x3, Kafka UI 9092 (broker), 8090 (UI, restringido) Los Security Groups siguen el principio de mínimo privilegio: el tráfico entre ec2-apps y ec2-mq/ec2-kafka se restringe por Security Group de origen (no por IP fija), y las interfaces de administración (RabbitMQ Management UI, Kafka UI) solo son accesibles desde la VPN/bastion de operaciones, nunca desde Internet. Estructura de compose.yml modular docker/ ├── apps/compose.yml # bff + microservicios core (perfil: apps) ├── mq/compose.yml # rabbitmq (perfil: mq) ├── kafka/compose.yml # zookeeper + kafka brokers + kafka-ui (perfil: kafka) └── .env.&lt;entorno&gt; # variables por entorno (dev/staging/prod) Cada archivo compose se despliega de forma independiente por servidor (docker compose --env-file .env.prod -f compose.yml up -d), permitiendo escalar o reiniciar cada capa sin afectar a las demás — condición necesaria para mantener el desacoplamiento operacional entre cómputo y mensajería. 2.2 Topología RabbitMQ — Tareas y Trabajo Asíncrono RabbitMQ gestiona el trabajo asíncrono de corta duración y orientado a comandos: envío de notificaciones, generación de certificados y recordatorios de sesión. Se despliega como clúster de 2 nodos con política de sincronización de colas espejo (ha-mode: all) para tolerar la caída de un nodo sin pérdida de mensajes en tránsito. Exchanges Exchange Tipo Propósito cmd.direct direct Enrutamiento 1:1 de comandos hacia su cola específica por routing key exacta. cmd.topic topic Enrutamiento por patrón (p. ej. session.*.reminder) para casos de notificación multi-destino. cmd.dead.dlx fanout Dead-letter exchange central: recibe todo mensaje rechazado (nack) o expirado (TTL) desde cualquier cola principal. Colas y bindings Cola principal Binding (exchange → routing key) Cola DLQ asociada TTL / reintentos q.cmd.email cmd.direct → cmd.email.send q.cmd.email.dlq 3 reintentos, TTL 30s, backoff exponencial q.cmd.session cmd.direct → cmd.session.reminder q.cmd.session.dlq 3 reintentos, TTL 60s q.cmd.certificate cmd.direct → cmd.certificate.issue q.cmd.certificate.dlq 3 reintentos, TTL 120s Cada cola principal declara x-dead-letter-exchange: cmd.dead.dlx y x-dead-letter-routing-key propio, de modo que un mensaje que agota sus reintentos cae en su DLQ homóloga (q.cmd.email.dlq, etc.) sin mezclarse con los de otras colas, preservando trazabilidad por tipo de comando. Envelope común de mensajes { &quot;type&quot;: &quot;SESSION_REMINDER&quot;, &quot;eventId&quot;: &quot;b3f1c2e4-...-uuid&quot;, &quot;timestamp&quot;: &quot;2026-09-08T14:30:00Z&quot;, &quot;traceId&quot;: &quot;9f2a...&quot;, &quot;correlationId&quot;: &quot;req-77af...&quot;, &quot;payload&quot;: { &quot;sessionId&quot;: &quot;...&quot;, &quot;studentEmail&quot;: &quot;...&quot; } } Todo consumidor valida idempotencia por eventId antes de ejecutar el efecto (envío de correo, emisión de certificado), registrando el identificador en un almacén de deduplicación (tabla o caché de corta duración) para descartar reentregas duplicadas típicas de la semántica at-least-once. Los ACK se emiten de forma manual y explícita solo tras persistir el efecto o confirmar el envío; el NACK con requeue=false se usa exclusivamente cuando el fallo es de negocio (no transitorio), enviando directo a DLQ. 2.3 Topología Apache Kafka — Streaming y Auditoría en Tiempo Real Kafka sostiene el registro inmutable de eventos de dominio y el historial de auditoría de la plataforma. El clúster se despliega con 3 nodos Zookeeper y 3 brokers Kafka, permitiendo tolerancia a la caída de un broker sin pérdida de datos gracias al factor de réplica 3. Tópico Particiones Factor de réplica Propósito Retención sessions.events 3 3 Eventos de dominio y cambios de estado de la máquina de estados de sesiones. 7 días audit.timeline 3 3 Historial detallado quién/qué/cuándo, insumo de ms-edututor-audit y ms-edututor-report. 30 días (compliance) sessions.events.DLT 3 3 Eventos que agotaron reintentos de procesamiento en consumidores. 14 días audit.timeline.DLT 3 3 Eventos de auditoría fallidos tras reintentos. 14 días Partition key: sessionId — garantiza el ordenamiento estricto de los eventos de una misma sesión (SOLICITADA → CONFIRMADA → ASIGNADA → EN_CURSO → REALIZADA/CANCELADA) dentro de la misma partición, evitando condiciones de carrera al reconstruir el estado en los consumidores. min.insync.replicas: 2 — tolera la caída de un broker sin bloquear la escritura, manteniendo durabilidad. Semántica de entrega: At-least-once con productor idempotente (enable.idempotence=true, acks=all) en ms-edututor-sessions; los consumidores implementan deduplicación por eventId antes de aplicar efectos en su read model. Dead Letter Topics (DLT): Tras 3 reintentos con backoff exponencial (Kafka Streams / consumer interceptor), el evento se republica en su tópico *.DLT con encabezados x-exception-message, x-original-topic y x-original-partition para diagnóstico sin bloquear el consumo del resto del tópico principal. Administración y monitoreo: se despliegan microservicios administradores livianos (rabbitmq-admin, kafka-admin) responsables del provisionamiento declarativo de exchanges/colas/tópicos al arrancar el entorno (infra-as-code aplicada vía API de gestión de cada broker) y de exponer métricas de salud hacia el stack de observabilidad. 3. Macro-Tarea 2 — Seguridad Centralizada, Identidad y Capa de Borde Esta capa concentra toda decisión de autenticación y autorización antes de que una petición llegue al dominio: identidad federada en Azure AD, validación del JWT en el borde (API Gateway) y aplicación de reglas de rol/permiso en el Backend for Frontend (BFF). Ningún microservicio interno vuelve a validar el token: confía en el contexto de identidad propagado por el BFF (Zero-Trust con verificación en el borde, propagación de contexto autenticado hacia adentro). 3.1 Gestión de Identidad (Azure AD / IDaaS) Elemento Valor / Configuración App Registration EduTutor Tenant ID &lt;TENANT_ID&gt; (variable de entorno, nunca hardcodeada) Client ID (API) &lt;API_CLIENT_ID&gt; — expuesto como audiencia api://&lt;API_CLIENT_ID&gt; Client ID (SPA) &lt;SPA_CLIENT_ID&gt; — usado por MSAL Angular con flujo Authorization Code + PKCE Roles / Claims (roles) Admin, Coordinador, Estudiante, Auditor Emisor (issuer) https://login.microsoftonline.com/&lt;TENANT_ID&gt;/v2.0 Los cuatro roles se definen como App Roles en el manifiesto de la App Registration y se asignan a usuarios/grupos desde Azure AD; Azure emite el claim roles dentro del JWT en cada login, evitando mantener una tabla de permisos duplicada en la aplicación. Rol Alcance funcional Admin Acceso total: KPIs globales, gestión de catálogo, auditoría completa. Coordinador Gestión operativa de sesiones pendientes, asignación de tutores, catálogo. Estudiante Solicitud y visualización de sus propias sesiones. Auditor Acceso de solo lectura a /api/audit/* y /api/report/*. 3.2 AWS API Gateway (HTTP API) — Punto de Entrada El API Gateway HTTP API actúa como frontera única de la red de microservicios. Termina la validación de autenticación mediante un JWT Authorizer nativo, de forma que ninguna petición sin token válido llega siquiera al BFF. # Configuración del JWT Authorizer (extracto conceptual, Terraform) resource &quot;aws_apigatewayv2_authorizer&quot; &quot;edututor_jwt&quot; { api_id = aws_apigatewayv2_api.edututor.id authorizer_type = &quot;JWT&quot; identity_sources = [&quot;$request.header.Authorization&quot;] jwt_configuration { issuer = &quot;https://login.microsoftonline.com/${var.tenant_id}/v2.0&quot; audience = [&quot;api://${var.api_client_id}&quot;] } } Enrutamiento: Toda ruta (/api/*) integra de forma privada (VPC Link) hacia ms-edututor-bff en ec2-apps; el Gateway no conoce ni expone directamente los microservicios de dominio. Throttling: Rate 1.000 req/s por cliente autenticado (JWT claim sub), Burst 2.000 req/s, con respuesta 429 estandarizada. Validación de esquema en el borde: Request Validators de API Gateway rechazan payloads malformados antes de facturar cómputo del BFF. 3.3 Backend for Frontend — ms-edututor-bff Implementado en Spring Boot como Resource Server de Spring Security. Es la única pieza que interpreta el JWT en profundidad (claims de rol, expiración, audiencia) y construye el contexto de identidad que propaga hacia los microservicios internos. # application.yml (ms-edututor-bff) spring: security: oauth2: resourceserver: jwt: issuer-uri: https://login.microsoftonline.com/${TENANT_ID}/v2.0 jwk-set-uri: https://login.microsoftonline.com/${TENANT_ID}/discovery/v2.0/keys # SecurityConfig.java (extracto) @Bean SecurityFilterChain filterChain(HttpSecurity http) throws Exception { http.authorizeHttpRequests(auth -&gt; auth .requestMatchers(&quot;/api/catalog/**&quot;).hasAnyRole(&quot;ADMIN&quot;,&quot;COORDINADOR&quot;) .requestMatchers(&quot;/api/sessions/solicitar&quot;).hasRole(&quot;ESTUDIANTE&quot;) .requestMatchers(&quot;/api/audit/**&quot;, &quot;/api/report/**&quot;).hasAnyRole(&quot;ADMIN&quot;,&quot;AUDITOR&quot;) .anyRequest().authenticated()) .oauth2ResourceServer(oauth2 -&gt; oauth2.jwt(jwt -&gt; jwt.jwtAuthenticationConverter(customRoleConverter()))); return http.build(); } El customRoleConverter() mapea el claim roles del token de Azure AD (Admin, Coordinador, Estudiante, Auditor) a GrantedAuthority de Spring (ROLE_ADMIN, etc.), habilitando las anotaciones @PreAuthorize a nivel de método en los controladores para reglas más finas que las de la cadena de filtros. Propagación de contexto downstream El BFF añade a cada llamada interna hacia catalog/sessions/audit/report un encabezado firmado internamente (X-User-Id, X-User-Roles, X-Correlation-Id) transportado sobre la red privada de la VPC; los microservicios de dominio confían en este contexto porque solo el BFF puede alcanzarlos (Security Group restringido al SG del BFF), materializando el principio de Zero-Trust con verificación centralizada en el borde y confianza transitiva controlada hacia adentro. 4. Macro-Tarea 3 — Ecosistema Backend de Dominio, Persistencia y Procesamiento Asíncrono Esta capa concentra la lógica de negocio, la persistencia relacional en Oracle y el patrón CQRS: los microservicios core transaccionales escriben el modelo de escritura y publican comandos/eventos; los microservicios consumidores construyen modelos de lectura especializados (auditoría, reportería) sin acoplarse a la base de datos transaccional ni penalizar su rendimiento. 4.1 Microservicios Core Transaccionales (Oracle DB) ms-edututor-catalog CRUD de asignaturas, tutores y bloques horarios. Control de disponibilidad y bloqueo optimista de cupos al confirmar una tutoría (columna de versión / SELECT ... FOR UPDATE según contención esperada). Base de datos propia (Oracle) — sin acceso directo desde ningún otro microservicio. ms-edututor-sessions CRUD de sesiones y máquina de estados estricta. Publicación de comandos hacia RabbitMQ (recordatorios, notificaciones) y streaming de eventos de dominio hacia Kafka (sessions.events). SOLICITADA → CONFIRMADA → ASIGNADA → EN_CURSO → REALIZADA ↘ CANCELADA (desde cualquier estado previo a EN_CURSO) Regla de invariante: una sesión NO puede transicionar a EN_CURSO sin tener asignación de tutor previa (estado ASIGNADA cumplido). // SessionStateMachine.java (extracto) public void transitionTo(SessionState target) { if (target == SessionState.EN_CURSO &amp;&amp; this.state != SessionState.ASIGNADA) { throw new IllegalStateTransitionException( &quot;No se puede iniciar una sesión sin tutor asignado: estado actual=&quot; + this.state); } if (!VALID_TRANSITIONS.get(this.state).contains(target)) { throw new IllegalStateTransitionException(this.state, target); } this.state = target; this.domainEvents.add(new SessionStateChangedEvent(this.id, target, Instant.now())); } Cada transición válida registra un evento de dominio en memoria (Transactional Outbox conceptual: la fila de sesión y el registro de evento se persisten en la misma transacción JDBC/JPA); un publicador asíncrono posterior lee la tabla outbox y publica hacia Kafka con productor idempotente, evitando el problema de doble escritura (dual-write) entre base de datos y broker. 4.2 Microservicios Consumidores y Analítica (Event-Driven &amp; Read Models) ms-edututor-notify (sin base de datos) Consumidor de RabbitMQ (q.cmd.email, q.cmd.session, q.cmd.certificate). Envío asíncrono de notificaciones (email/webpush) y tickets de sesión para tutores. Manejo de reintentos con backoff y desvío a DLQ tras agotar el máximo configurado por cola; no persiste estado propio, por lo que su escalado horizontal es trivial (stateless). ms-edututor-audit (Oracle DB) Consumidor de Kafka de sessions.events y audit.timeline. Persistencia de la trazabilidad completa (quién/qué/cuándo) en su propio esquema Oracle, desacoplado del esquema transaccional de sessions/catalog. Expone API de solo lectura: GET /api/audit/timeline, GET /api/audit/session/{id}, con filtros por usuario, fecha y tipo de evento. ms-edututor-report (Oracle DB) Consumidor de Kafka para agregación de métricas, aplicando el lado de lectura (Query) del patrón CQRS sin tocar el esquema transaccional del lado de escritura (Command). Procesa eventos de forma incremental (ventKing por hora) para mantener tablas de agregados pre-calculadas. Endpoints analíticos: GET /api/report/kpis, GET /api/report/top-services — sesiones por hora, tasas de asistencia y estados activos. @KafkaListener(topics = &quot;sessions.events&quot;, groupId = &quot;report-service-v1&quot;) public void onSessionEvent(ConsumerRecord&lt;String, String&gt; record) { SessionEvent event = deserialize(record.value()); if (dedupStore.alreadyProcessed(event.eventId())) return; // idempotencia try { aggregationService.applyToHourlyBucket(event); dedupStore.markProcessed(event.eventId()); } catch (TransientException e) { throw e; // reintento gestionado por el contenedor de listeners } catch (BusinessException e) { kafkaTemplate.send(&quot;sessions.events.DLT&quot;, record.key(), enrich(record, e)); } } La separación entre comando (sessions/catalog, consistencia fuerte, Oracle transaccional) y consulta (audit/report, consistencia eventual, modelos de lectura optimizados) permite escalar cada lado de forma independiente: los picos de lectura de KPIs en /dashboard nunca compiten por conexiones con la escritura de nuevas sesiones. 5. Macro-Tarea 4 — Frontend Web, Integración End-to-End y Puesta en Marcha Esta capa entrega la experiencia de usuario final, consumiendo de forma segura las APIs expuestas por el BFF y validando el flujo íntegro de la plataforma sobre el entorno EC2 desplegado. 5.1 Frontend Angular con MSAL Integración con @azure/msal-angular para el flujo «Iniciar sesión con Microsoft» (Authorization Code Flow + PKCE, sin flujo implícito). Route Guards (MsalGuard + un RoleGuard propio) que restringen la navegación según el claim roles del token, redirigiendo a una vista 403 cuando el rol no habilita la ruta. HTTP Interceptor (MsalInterceptor) que adjunta automáticamente Authorization: Bearer &lt;access_token&gt; a toda petición hacia el dominio del API Gateway, y renueva el token de forma silenciosa (silent token acquisition) antes de que expire. // msal.config.ts (extracto) export const msalConfig: Configuration = { auth: { clientId: environment.spaClientId, authority: `https://login.microsoftonline.com/${environment.tenantId}`, redirectUri: environment.redirectUri, }, cache: { cacheLocation: &quot;sessionStorage&quot; }, }; export const protectedResources = { edututorApi: { endpoint: environment.apiGatewayUrl, scopes: [`api://${environment.apiClientId}/access_as_user`], }, }; 5.2 Implementación de Pantallas y Casos de Uso Ruta Rol(es) con acceso Descripción /login Público Portal de autenticación contra Azure AD. /dashboard Todos (contenido adaptado) Admin ve KPIs globales; Coordinador ve sesiones pendientes; Estudiante ve sus próximas sesiones. /sessions Admin, Coordinador, Estudiante Listado, solicitud de sesiones y transiciones de estado. /catalog Admin, Coordinador Mantenimiento de asignaturas, tutores y bloques de horario. /reports Admin, Auditor Visualización gráfica de KPIs, horas punta y asistencia. /audit Admin, Auditor Timeline cronológico de auditoría con filtros por usuario, fecha y evento. El diseño visual evita la estética genérica de degradados morados y tipografías de sistema sin identidad: se recomienda una paleta sólida basada en tonos navy/teal (coherente con el dominio educativo institucional), tipografía con jerarquía marcada para separar KPIs de contenido tabular, y micro-interacciones (skeleton loaders, transiciones de estado en /sessions) que comuniquen claramente los estados de carga, éxito y error en cada llamada asíncrona al BFF. 5.3 Validación End-to-End y Despliegue Integral La validación E2E recorre la cadena completa desplegada en AWS EC2, confirmando que cada frontera (Gateway, BFF, brokers) aplica correctamente sus contratos: Angular (MSAL) → API Gateway (JWT) → ms-edututor-bff → ms-edututor-sessions / ms-edututor-catalog (Oracle) → RabbitMQ (q.cmd.*) → ms-edututor-notify → Kafka (sessions.events, audit.timeline) → ms-edututor-audit (Oracle) → /api/audit/* → ms-edututor-report (Oracle) → /api/report/* Caso feliz: login → solicitud de sesión → confirmación → asignación → inicio → finalización, verificando que cada transición aparece en /audit y en las métricas de /reports. Tolerancia a fallos en mensajería: se simula la caída del servicio de correo (ms-edututor-notify) y se verifica que los mensajes agotan reintentos y aterrizan en q.cmd.email.dlq sin bloquear el resto de la cola. Tolerancia a fallos en streaming: se fuerza un evento malformado hacia sessions.events y se confirma su enrutamiento a sessions.events.DLT sin detener el consumer group de report/audit. Verificación de control de acceso: un usuario con rol Estudiante intenta acceder a /api/report/kpis y recibe 403 tanto desde el interceptor de Angular como (defensa en profundidad) desde el BFF. 6. Resiliencia, Observabilidad y Hardening Transversal Los siguientes criterios aplican de forma transversal a las cuatro macro-tareas y constituyen la base de operación en producción del sistema. 6.1 Trazabilidad de extremo a extremo Todo request que ingresa por el API Gateway recibe (o propaga, si ya viene provisto) un X-Correlation-Id que se inyecta en los logs estructurados del BFF, en los encabezados de los mensajes de RabbitMQ y en los headers de los eventos de Kafka, permitiendo reconstruir el recorrido completo de una solicitud de estudiante a través de las cinco capas del sistema durante el diagnóstico de incidentes. 6.2 Métricas Clave (SLI/SLO) Métrica (SLI) Umbral / SLO Acción de alerta kafka_consumergroup_lag (audit / report) &gt; 500 mensajes sostenidos por 3 min Auto-scaling del consumidor + alerta a guardia rabbitmq_queue_depth (q.cmd.*) &gt; 200 mensajes sostenidos por 5 min Alerta; investigar ms-edututor-notify rabbitmq_dlq_rate &gt; 1% de mensajes entrantes Alerta crítica — posible fallo sistémico de notificación api_gateway_5xx_rate &gt; 1% en ventana de 5 min Alerta crítica al equipo de plataforma bff_jwt_validation_latency_p99 &gt; 150 ms Revisar caché de JWKS de Azure AD oracle_connection_pool_saturation &gt; 85% de uso sostenido Escalar pool / revisar consultas lentas en catalog 6.3 Seguridad Zero-Trust Terminación de TLS en el API Gateway; tráfico interno dentro de la VPC restringido por Security Groups nombrados (no por rangos CIDR amplios). Ningún microservicio de dominio expone puerto público; solo son alcanzables desde el Security Group del BFF. Secretos (credenciales Oracle, credenciales RabbitMQ, client secret de Azure AD) gestionados en AWS Secrets Manager, nunca en variables de entorno planas ni en el repositorio. 6.4 Infraestructura como Código El aprovisionamiento de EC2, Security Groups, API Gateway y sus integraciones se mantiene versionado (Terraform), y el provisionamiento declarativo de exchanges/colas de RabbitMQ y tópicos de Kafka se ejecuta mediante los microservicios administradores al desplegar cada entorno, evitando configuración manual divergente entre desarrollo, staging y producción. 7. Conclusiones La arquitectura de EduTutor separa con claridad tres preocupaciones que suelen mezclarse en sistemas monolíticos: la identidad y el control de acceso (Macro-Tarea 2), la consistencia transaccional del dominio (Macro-Tarea 3, lado de comando) y la construcción de vistas analíticas y de auditoría desacopladas (Macro-Tarea 3, lado de consulta), todo ello sostenido por una infraestructura de mensajería dual — RabbitMQ para trabajo asíncrono puntual y Kafka para streaming de eventos inmutables — que se aprovisiona y opera de forma reproducible (Macro-Tarea 1) y se consume finalmente a través de una experiencia de usuario coherente y segura por rol (Macro-Tarea 4). El resultado es un sistema que tolera fallos parciales (caída de un broker, un mensaje malformado, un servicio de notificación caído) sin comprometer la disponibilidad del flujo transaccional principal, y que mantiene trazabilidad completa de cada decisión de negocio a través de X-Correlation-Id, los tópicos de auditoría y las Dead Letter Queues/Topics.
